# ADR 0001 — The wire format comes from formstr-drive's source, at a pinned SHA

**Status:** accepted, 2026-09-29

## Context

`@formstr/drive-sdk` 0.1.0 implemented NIP-FS from the spec text. The app it has to
interoperate with, `formstr-hq/formstr-drive`, kept moving: single-blob encryption
(#69), dedup and upload preflight (#70), file and folder sharing (#71), and seekable
previews (#72). Nothing compared the SDK against what the app actually publishes, so
every test checked the SDK against the SDK.

The gap was not cosmetic. Reading the app at the top of that stack shows behaviour the
0.1.0 SDK did not have at all:

| | SDK 0.1.0 | formstr-drive @ `0064bff` |
|---|---|---|
| Drive Key payload | `{encryptionKey}` only | also `{encryptionKey, previousKeys}`, and a legacy `[["encryptionKey", hex]]` array |
| Drive Key lookup | nullable; README suggested `current ?? mint` | three-state status; minting gated on a relay-coverage proof |
| Metadata author | identity signer | the **Drive Key** (`finalizeEvent`), no signer prompt |
| Tag order | `d, t, encrypted, client` | `d, t, client, encrypted` |
| File payload | `parent`, `servers[]` | `folder` (a path string), `id`, `server`, `deleted` |
| Sharing | one ephemeral-key event | `s-` shares, `si-` bookkeeping, naddr links, revoke |
| Upload | PUT to every server | BUD-06 preflight, fallback, honest failure reporting |

A client speaking the left column cannot read a drive written by the right column.

## Decision

The wire format is **read from `formstr-hq/formstr-drive` source at the pinned SHA
`0064bffcef4ecf73ae153894cce6a75b674f014d`** (branch `feat/seekable-previews`, PR #72,
the top of stacked PRs #69–#72). Not from the README, not from the NIP text alone, not
from another client's copy of the protocol.

Where the app and the spec disagree, the app is what real drives contain, so the
**reader** follows the app (ADR 0002) while the **writer** follows the spec.

Each section of `docs/protocol.md` names the app function it mirrors. To update:
diff the app against the pinned SHA, change `protocol.md` first, the codecs second,
and bump the SHA here last.

## Verification

The SDK's tests build their fixtures from `docs/protocol.md` and check the result two ways:
what the SDK **writes** is decoded with stock `nostr-tools` alone (`nip19.decode`,
`nip44.v2.decrypt`, no SDK code in the decode path — `test/interop.test.ts`), and what it
**reads** is exercised against both the spec shape and the app's shape written out by hand
(`test/signing.test.ts`, `test/sharing.test.ts`, `test/blob.test.ts`).

An earlier revision of this change also checked the SDK against vectors generated by running
the app's own code at the pinned SHA. They were removed so that nothing executable depends on a
specific commit staying reachable (the pinned commit lives on a feature branch and is not an
ancestor of `main`, since the PRs were squash-merged). The cost is real: nothing in CI now proves
the SDK decodes what the app *actually* emits. Until that is automated again, re-check by hand
before a release: diff the app's `src/` against the SHA recorded here.

## Notes

- Upstream `main` (`edfb27c`, after #69–#72 were merged) differs from the pinned tree only by two
  lines adding `wss://relay.formstr.app` to the default relay lists in `src/utils/common.ts`,
  which is not part of the wire format. If the pin ever has to be re-anchored, `edfb27c` is the
  durable equivalent.
- The app's own metadata events are stamped with the plain wall clock, not a monotonic one,
  so two edits inside one second tie and relays keep the lower id. The SDK's `nextCreatedAt`
  avoids this for what it writes; it cannot fix what the app writes.
